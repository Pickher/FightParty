# FightParty 项目规划：从功能原型到完整可玩版本

更新：2026-11-14（北京时间）。评估基线：`cloud/test`，源码 v0.11.3，`a86576d`。

本规划针对三个目标：完整的规则与体验、清楚且有质感的交战动画和场景、能够观察对手并作出有效应对的博弈。此次只审阅源码、配置、文档和资源，不运行游戏、模拟、测试或打包；下文的风险判断不是实战验证结果。任务执行与验收记录放在 [待办清单](PROJECT_BACKLOG.md)。

## 1. 项目判断

当前定位是“机制较丰富、已有对局闭环的离线原型”。配兵、周期经济、出兵、推进、自动战斗、建筑目标、胜负和重开已经有代码；公共单位、武器、技能框架也已搭好。接下来最值得投入的是把这些系统收束成一套能读懂、能完成、能复盘的体验，再扩大内容量。

不宜给一个整体完成百分比：有代码、运行正确、达到体验标准是三种不同状态。尤其近几轮机制与数据修改按约定没有运行验证，不能把历史测试通过视为当前版本通过。

| 领域 | 当前已有 | 距离目标的主要缺口 | 依据 |
| --- | --- | --- | --- |
| 基础对局 | 离线 1v1、永久兵营、波次、残兵、终局判定、重开 | 当前规则手册统一、对局时长与僵局体验、完整一局验收 | `scripts/battle_sim.gd`、`data/rules.json` |
| 经济与地图 | 196×118 地图、矿气收入、中央井、宝库、玩家选址建塔 | 资源选择的实际价值、侧向空间的用途、不同防线的收益 | `scripts/economy/desert_storm_economy.gd`、`docs/DESERT_STORM_ECONOMY.md` |
| 兵种与战斗 | 52 个配置实体；43 个可购 ready 单位，其中人 11、虫 11、神 10、腐 11；另有 3 个召唤物、6 个建筑/防御配置 | 可购不等于技能齐全；来源记录有 233 条待确认项，需要逐项决定采用值或正式简化 | `data/units.json`、`data/units/desert_storm_reference.json` |
| 可复用架构 | 单位模板/实例、独立技能、独立武器、射弹/光束/推进线、分段攻击、独立炮位 | 不需要重做框架；需要统一各表现事件的语义、减少新增美术时的专属接线 | `scripts/units/`、`scripts/skills/`、`scripts/attacks/` |

## 2. 优先解决的六个问题

**规则口径混杂。** README、DESIGN 等同时保存旧地图、旧收入和旧数值说明。新开发者和玩家可能照着过期规则理解游戏。先建立唯一的“当前规则”，历史变化另存；配置、Excel、UI 与文档须明确各自职责。

**对局可能过长。** 默认首波 65 秒、后续 45 秒、64 波，最后一波时间为 `65 + 63×45 = 2900 秒`，即 48 分 20 秒；再加终局上限 600 秒，最长约 58 分 20 秒游戏时间，暂停另计，也可能提前摧毁基地结束。这是配置推算，不是测得的平均局长。建议先把常规局 20～30 分钟、快速验证局 8～12 分钟作为讨论起点；这会偏离原图节奏，不能未经定版直接压缩波次并保留旧经济。

**电脑可能无法积累高价反制。** 收入到账会触发购买，目标买不起时 AI 会改买当前便宜单位；除攒塔外缺少明确的攒兵计划。需要先修正这类决策限制，再用 AI 判断玩家阵容是否过强。不能拿弱 AI 的失败直接证明某兵种失衡。

**多种资源未形成同等完整的选择。** 灵核已有奖励和显示，当前没有实际消费配置；瓦斯的明确消费场景很少，免费分流、1:1 兑换本身也不等于经营深度。中央井的固定 +3 收益相对 30/60/120 基础收入逐渐下降。先判断这些机制是否提供可理解的取舍，再决定补全用途、明确为战绩，或缩减首版展示；不凭空添加一整套科技树。

**画面空间比批量建模更紧迫。** 现有 1300×352 战场区域搭配 196×118 地图、默认 2 倍缩放，0.8 格单位主体仅约 4.8 个设计像素，1152 宽窗口下约 3.8 像素。这是源码尺寸推算；透明留白不等于主体大小。需要可看战斗的近景与可看全局的导航，否则精细动画投入也难被看见。

**完整性与“复刻全部原作”尚未分开。** 当前很多单位有简化技能、未研究升级或未做效果。不是每个 `pending` 都必须照搬：每项应标明“首版实现、正式简化、首版排除、待确认”。隐身若进入首版，必须同时有探测、提示和 AI 对策；只加隐身会破坏可反制性。

## 3. 建议的首个完整版本边界

以下是规划建议，还没有改动游戏开关、数值或现有可选种族。

- 以 **Windows + Android 的离线 1v1** 为首版，完成开局、学习、配兵、战斗、胜负、复盘和重开。
- 以人族、虫族、神族现有 **32 个可购单位** 为候选验收范围；每个进入正式名单的单位都有明确定位、可用武器/技能、完整表现和可反制手段。缺口无法及时补齐时，明确缩小正式名单，避免把原型状态当成完成。
- 腐族现有 11 个 ready 单位保留为实验内容，暂不纳入三族平衡承诺；正式入口是否标识/隔离由范围定版任务处理，不在此次规划中擅自下架。
- 延续已有自动战斗与波前配兵玩法、组件框架、“特战队员”名称、Excel 编辑流程。原图明确配置仍为数据依据，新的自主平衡修改必须记录原因。
- 暂缓联网/排位/多人轮流出兵、指挥官体系、完整 SC2 科技树、腐族扩展、iOS 发布。新增普通兵种只为填补已证实的阵容缺口。
- 迷雾、隐身探测、可改变路径的地形、复杂经济扩展均需要完整规则和反制设计。装饰性沙漠场景可以先做；装饰不自动获得阻挡或高低地效果。

## 4. 里程碑与完成条件

阶段按交付物推进，不按未经估算的固定日期承诺。玩法程序与美术可在规则接口稳定后并行。

| 阶段 | 交付物 | 通过条件 | 任务与依赖 |
| --- | --- | --- | --- |
| M0 规则定版 | 当前规则页、首版名单、局长/经济/科技取舍、资料缺口分类 | 同一个规则在配置、表格说明、UI 和文档中没有互相矛盾的口径；首版范围明确 | R01～R05；先做 |
| M1 规则与决策闭环 | 资源/终局收口、AI 攒钱与组合计划、战斗边界规则、最小战报指标 | 能解释钱怎么花、为什么出这些兵、什么时候结束；关键边界进入待验场景 | R06～R12；依赖 M0 |
| M2 可展示的战斗样板 | 镜头与界面样板、统一动画接入规范、代表兵种、场景、音效和引导样板 | 在约定窗口/手机上看清敌我、出手、命中、死亡与关键技能；画面与结算一致 | V01～V08；可与 M1 部分并行 |
| M3 博弈成立 | 三族阵容角色表、可行策略、反制矩阵、地图/塔/经济平衡记录、AI 难度 | 不靠隐藏补贴；存在至少 3 种有机会成本的可行组合与对应反制；调整有记录 | G01～G07；依赖 M1，使用 M2 表现帮助判断 |
| M4 内容与体验补齐 | 正式名单的动画/图标/建筑/技能表现，完整场景音频、手机操作与恢复方案 | 正式内容无临时占位；关键操作在手机可完成；从开局到结算流程一致 | A01～A05、U01～U03；以 M2 规范为基础 |
| M5 验收与交付 | 当前基线验证记录、Windows/Android 安装包、版本说明和下载入口 | 无阻断问题；已安排的规则/设备验收通过；安装包可追溯至源码提交 | Q01～Q05；依赖前述交付，验证由用户安排 |

推荐先排入下一轮的任务：**R01 当前规则、R02 首版范围、R03 节奏与经济决策、R09 AI 攒钱、V01 镜头布局**。R09 的目标价格以定版配置为准；V01 可以先制作布局样板，不依赖全部兵种美术。

M2 的代表兵种建议为：特战队员（既有样板）、坦克（部署/炮击）、医疗兵（持续治疗）、穿刺者（埋地/推进线）、巨像（双束扫射）、大和舰（既有移动攻击/大招样板）。补充一组普通近战的移动/受击样板，避免只验证远程单位。无需等待全部 32 个单位完成才能发现接入问题。

## 5. 博弈设计的落点

| 玩家选择 | 希望产生的取舍 | 要补上的支撑 |
| --- | --- | --- |
| 低价即时增援 / 攒钱买关键单位 | 当下战线与未来反制之间取舍 | 可负担时间提示；AI 也会攒钱；高价单位有弱点 |
| 密集保护后排 / 分散降低溅射 | 支援覆盖与范围伤害之间取舍 | 阵型能实际影响接战，单位不马上挤成同一团 |
| 地面主力 / 对空投入 / 空军绕过地面火力 | 投资与对手阵容变化之间取舍 | 空地信息可见、各族有可购买的应对、无单一万能组合 |
| 机动推进 / 部署防守 | 先到战场与建立火力区之间取舍 | 架设稳定、射程差可见、可被近身/转线等方式利用 |
| 保护宝库 / 前压建塔 / 争夺中央 | 安全、距离、收益之间取舍 | 选址具有实际影响；塔不会长时间封死对局；避免不可反制的前置塔 |
| 根据上一波反制 / 延迟暴露新阵容 | 已知信息与预测之间取舍 | 保留不偷看下一波的约束；复盘解释失败原因，AI 使用同等信息 |

平衡不是让三族塔的血量、面板 DPS 一样：需要同时看价格、护甲、护盾恢复、射程、空地分配、独立目标数、溅射和部署位置。当前虫族塔调整是待验证起点。建议比较等预算、混合空地、不同阵型、推进/守点和长时间续战，单挑与木桩 DPS 只作辅助证据。

## 6. 验收办法与执行节奏

| 目标 | 建议验收办法（后续安排，不是本次已执行） |
| --- | --- |
| 规则完整 | 从空阵容到结束走完整流程；复核未出场退款、资源不足、空地无法互攻、召唤物残留、同时破基地、终局超时等场景；当前手册能解释结果 |
| 新玩家能上手 | 邀请不了解项目的人：在引导下独立完成买兵、布阵、看敌情、一次反制和建塔；记录停顿与误操作原因 |
| 战斗可读 | 用普通速度回看样板交战；能辨认谁在攻击谁、是否命中、为何死亡；缩放后仍分得清主要兵种与空地层 |
| 有博弈 | 固定版本记录预算、阵容、阵型、波次、胜负和剩余战力；每族至少有两种不同开局方向；强势组合有可执行的回应，避免单凭主观输赢调数值 |
| 节奏合理 | 记录首次交战、首次有效购买选择、空跑/等待时间、结束波次与总时长；再决定调整地图、波次还是经济，避免同时改动所有变量 |
| 性能与手机 | 先指定代表设备与单位规模；建议普通战斗以 60 FPS 为目标，低档/高密度场景以稳定 30 FPS 为底线候选；固定步不能长期积压，最终预算经实测确认 |
| 可交付 | 实机安装、升级、暂停/恢复与退出行为可理解；下载得到的版本/提交/校验值一致；源码更新不冒充 APK 更新 |

遵守现有约定：**日常实现不自动运行模拟、测试或打包。** 阶段产物先标记“待验收”，用户安排验证时集中执行所需场景；未执行的检查不能写成通过。已有测试优先迁移关键规则，不为文案、低影响改动或实现细节堆测试。

每次选一个主要功能任务，最多并行一个互不冲突的美术任务；提交说明写明任务 ID、行为变化、未验证项。完成时记录源码提交和验收证据，不能只凭“代码已写”勾选完成。原型试做和美术样板可以先交付，数值平衡在同一固定版本上评估。

## 7. 风险与范围控制

| 风险 | 处理方式 |
| --- | --- |
| 一边反复改规则，一边批量做动画 | 先定武器时序/事件与美术规范，完成样板后复用；动画服从模拟时间 |
| 参考图继承数据不全 | 逐项记录来源与项目采用值；233 条记录不是 233 个确定 Bug，也不是都必须还原 |
| 只凭面板强弱调整，改坏克制关系 | 保留单次改动原因与对照阵容；先修 AI/索敌/命中问题，再调伤害 |
| 新内容越加越多，始终不能交付 | 首版名单定版后新增需求进入 P2；只有阻断首版体验的缺口才能插队 |
| 地形看似能挡兵，实际上没有碰撞 | 先用明确不阻挡的装饰；需要阻挡时再成套设计寻路与空地差异 |
| 当前测试/文档与配置脱节 | 建立当前基线与历史档案边界；按阶段集中验收，保留未验证说明 |
| 长局手机被系统回收后丢失进度 | 明确中途恢复方案；暂停已实现，但进程重启后的续局尚未实现 |

任务清单中的 P0 是规则和关键体验前置，P1 是首个完整版本的交付工作，P2 是后续候选。P0/P1 不代表已批准执行全部功能；本次交付的是可逐项安排的规划。
